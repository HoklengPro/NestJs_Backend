== 🔑 Key Concepts Before We Start

=== What is Dependency Injection (DI)?

*Dependency Injection* is a design pattern where a class *does NOT create its own dependencies*. Instead, the NestJS *IoC (Inversion of Control) container* creates them and *injects* them through the constructor.

*Why is this important?*

|===
|Without DI (Bad) |With DI (Good)

|`new NotificationsService()` — you create it yourself
|`constructor(private notifications: NotificationsService)` — NestJS creates and injects it

|Tightly coupled — hard to test, hard to swap
|Loosely coupled — easy to test with mocks, easy to swap implementations

|If constructor changes, ALL files must update
|NestJS handles it — your code doesn't care how it's built
|===

=== What is a Circular Dependency?

A *circular dependency* happens when *Service A depends on Service B*, AND *Service B depends on Service A*. NestJS cannot figure out which one to create first — it's like a chicken-and-egg problem.

----
OrdersService → needs NotificationsService
NotificationsService → needs OrdersService
                ↑ WHO gets created first???
----

NestJS will crash with: `"A circular dependency has been detected"`

=== Step 1: Create NotificationsService (Simple Provider)

.File: `src/notifications/notifications.service.ts` (initial version)
[source,typescript]
----
import { Injectable } from '@nestjs/common';

@Injectable()
export class NotificationsService {
  notify(event: string, payload: any) {
    console.log(`[NOTIFY] ${event}`, payload);
    return { ok: true };
  }
}
----

*Line-by-line explanation:*

|===
|Line |Explanation

|`@Injectable()`
|This decorator marks the class as a *NestJS provider*. It tells the IoC container: "you can create instances of this class and inject it into other classes." Without `@Injectable()`, NestJS would throw an error when another service tries to use it.

|`notify(event: string, payload: any)`
|A method that takes an *event name* (like `'receipt_created'`) and a *payload* (data about the event). For this lab, it simply logs to the console. In a real app, this might send emails, push notifications, or publish to a message queue.

|`console.log(\`[NOTIFY] ${event}\`, payload)`
|Uses template literals to log the event. `${event}` is string interpolation — it inserts the value of `event` into the string. The `[NOTIFY]` prefix makes it easy to find in logs.

|`return { ok: true }`
|Returns a simple confirmation object. In production, you might return a message ID or delivery status.
|===

*Teacher may ask:*

* *What does `@Injectable()` do?* — It marks the class as a provider that the NestJS DI container can manage. Without it, NestJS cannot create or inject this class.
* *Can a class without `@Injectable()` be injected?* — No. NestJS needs this decorator to read metadata (constructor parameter types) for dependency resolution.
* *Is NotificationsService a singleton?* — Yes, by default. NestJS creates ONE instance and shares it everywhere. This is the default `SINGLETON` scope.

=== Step 1b: Register NotificationsModule and Export the Service

For other modules to use `NotificationsService`, we must:

1. Add `NotificationsService` to `exports[]` in `NotificationsModule`
2. Import `NotificationsModule` in `AppModule`

.File: `src/notifications/notifications.module.ts` (initial version)
[source,typescript]
----
import { Module } from '@nestjs/common';
import { NotificationsService } from './notifications.service';

@Module({
  providers: [NotificationsService],
  exports: [NotificationsService], // ✅ Makes it available to other modules
})
export class NotificationsModule {}
----

*Why `exports: [NotificationsService]` is required:*

In NestJS, providers are *private to their module by default*. Only the module that declares a provider can use it. If `ReceiptsModule` wants to inject `NotificationsService`, then `NotificationsModule` MUST export it. Without `exports`, you get:

----
Error: Nest can't resolve dependencies of ReceiptsService (?). 
Please make sure that the argument NotificationsService is available in ReceiptsModule.
----

*The rule:*

* Module A wants a provider from Module B → Module A must `imports: [ModuleB]`
* Module B must `exports: [TheProvider]` to make it visible

=== Step 2: Inject NotificationsService into ReceiptsService

Now we use DI to inject `NotificationsService` into `ReceiptsService`, so that every time a receipt is created, a notification is triggered.

.File: `src/receipts/receipts.service.ts` (updated)
[source,typescript]
----
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Receipt } from 'src/database/entities/receipts.entity';
import { CreateReceiptDto } from './dto/create-receipt.dto';
import { UpdateReceiptDto } from './dto/update-receipt.dto';
import { NotificationsService } from 'src/notifications/notifications.service'; // ✅ NEW import

@Injectable()
export class ReceiptsService {
  constructor(
    @InjectRepository(Receipt)
    private readonly receiptRepo: Repository<Receipt>,
    private readonly notifications: NotificationsService, // ✅ DI — NestJS injects this
  ) {}

  async findAll() {
    return this.receiptRepo.find({ order: { issuedAt: 'DESC' } });
  }

  async findOne(receiptId: string) {
    const receipt = await this.receiptRepo.findOne({ where: { receiptId } });
    if (!receipt) throw new NotFoundException('Receipt not found');
    return receipt;
  }

  async create(dto: CreateReceiptDto) {
    const receipt = this.receiptRepo.create({
      issuedAt: new Date(dto.issuedAt),
      name: dto.name,
      price: dto.price,
    });
    const saved = await this.receiptRepo.save(receipt);

    // ✅ NEW — Notify after receipt is created
    this.notifications.notify('receipt_created', {
      receiptId: saved.receiptId,
      price: saved.price,
    });

    return saved;
  }

  async update(receiptId: string, dto: UpdateReceiptDto) {
    const receipt = await this.findOne(receiptId);
    if (dto.issuedAt !== undefined) receipt.issuedAt = new Date(dto.issuedAt);
    if (dto.name !== undefined) receipt.name = dto.name;
    if (dto.price !== undefined) receipt.price = dto.price;
    return this.receiptRepo.save(receipt);
  }

  async remove(receiptId: string) {
    const receipt = await this.findOne(receiptId);
    await this.receiptRepo.remove(receipt);
    return { deleted: true, receiptId };
  }
}
----

*What changed:*

1. Added `import { NotificationsService }` — to reference the class type
2. Added `private readonly notifications: NotificationsService` in the constructor — NestJS will inject it automatically
3. Called `this.notifications.notify(...)` inside `create()` — fires a notification event after saving

*How the DI chain works:*

----
ReceiptsService
  ├── @InjectRepository(Receipt) → Repository<Receipt>  (provided by TypeOrmModule.forFeature)
  └── NotificationsService                               (provided by NotificationsModule)
----

NestJS resolves ALL constructor dependencies before creating `ReceiptsService`. If any dependency is missing, the app crashes at startup — NOT at runtime.

import { Column, Entity, PrimaryGeneratedColumn, CreateDateColumn } from 'typeorm';

@Entity()
export class Order {
  @PrimaryGeneratedColumn('uuid')
  orderId: string;
  // ↑ Auto-generated UUID primary key, same as Receipt

  @Column()
  item: string;
  // ↑ Name of the ordered item (e.g., "Laptop")

  @Column({ default: 1 })
  quantity: number;
  // ↑ How many of this item. Defaults to 1 if not provided.
  //   { default: 1 } tells PostgreSQL: if no value is inserted, use 1.

  @Column({ type: 'decimal', precision: 10, scale: 2 })
  price: number;
  // ↑ Same as Receipt — decimal for exact money values

  @CreateDateColumn()
  createdAt: Date;
  // ↑ @CreateDateColumn() is a special TypeORM decorator.
  //   It automatically sets the value to the current timestamp when the row is INSERTED.
  //   You NEVER set this manually — TypeORM does it for you.
  //   SQL equivalent: DEFAULT CURRENT_TIMESTAMP
}
----

*Teacher may ask:*

* *What is `@CreateDateColumn()`?* — A decorator that automatically sets the column value to the current date/time when a new row is inserted. You don't pass it in your DTO or service — TypeORM handles it.
* *What is `{ default: 1 }` in `@Column()`?* — Sets a default value at the database level. If the INSERT query doesn't include `quantity`, PostgreSQL uses `1`.
* *Difference between `@CreateDateColumn()` and `@Column({ type: 'timestamp' })`?* — `@CreateDateColumn()` auto-fills on insert. `@Column({ type: 'timestamp' })` requires you to set the value manually.

.File: `src/orders/dto/create-order.dto.ts`
[source,typescript]

import { IsNotEmpty, IsNumber, IsOptional, Min } from 'class-validator';

export class CreateOrderDto {
  @IsNotEmpty()
  item: string;
  // ↑ Required field — cannot be empty string or missing

  @IsOptional()
  @IsNumber()
  @Min(1)
  quantity?: number;
  // ↑ Optional — if not provided, the entity default (1) is used
  //   @Min(1) — quantity must be at least 1 (you can't order 0 items)

  @IsNumber()
  @Min(0)

  // ↑ Required — must be a number >= 0
}

.File: `src/orders/orders.service.ts`
[source,typescript]
----
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Order } from 'src/database/entities/order.entity';
import { CreateOrderDto } from './dto/create-order.dto';
import { NotificationsService } from 'src/notifications/notifications.service'; // ✅

@Injectable()
export class OrdersService {
  constructor(
    @InjectRepository(Order)
    private readonly orderRepo: Repository<Order>,
    private readonly notifications: NotificationsService, // ✅ DI
  ) {}

  async createOrder(dto: CreateOrderDto) {
    const order = this.orderRepo.create({
      item: dto.item,
      quantity: dto.quantity ?? 1,
      // ↑ Nullish coalescing: if dto.quantity is null or undefined, use 1.
      //   This matches the entity's { default: 1 } but applies at the application level.
      price: dto.price,
    });

    const saved = await this.orderRepo.save(order);
    // ↑ INSERT INTO order ("item", "quantity", "price") VALUES (...) RETURNING *
    //   PostgreSQL auto-generates orderId (UUID) and createdAt (timestamp)

    this.notifications.notify('order_created', {
      orderId: saved.orderId,
      item: saved.item,
      price: saved.price,
    });
    // ↑ After saving, send a notification event.
    //   This logs: [CORE EVENT] order_created { orderId: '...', item: 'Laptop', price: 999.99 }

    return saved;
  }

  async findAll() {
    return this.orderRepo.find({ order: { createdAt: 'DESC' } });
    // ↑ SELECT * FROM "order" ORDER BY "createdAt" DESC
    //   Returns all orders, newest first
  }
}
----

*Key point: `dto.quantity ?? 1` explained:*

* `??` is the *nullish coalescing operator*
* It returns the right-hand side ONLY if the left-hand side is `null` or `undefined`
* If client sends `{ "item": "Laptop", "price": 999 }` → `dto.quantity` is `undefined` → uses `1`
* If client sends `{ "item": "Laptop", "quantity": 3, "price": 999 }` → `dto.quantity` is `3` → uses `3`
* This is different from `||` which also triggers on `0` or `""` (which might be valid values)

*What happens when you run the app:*

----
ERROR [ExceptionHandler] Nest cannot create the NotificationsModule instance.
A circular dependency has been detected between modules.
NotificationsModule → OrdersModule → NotificationsModule
----

*Why NestJS crashes:*

1. NestJS tries to create `OrdersModule`
2. `OrdersModule` needs `NotificationsModule` (because `imports: [NotificationsModule]`)
3. So NestJS tries to create `NotificationsModule` first
4. But `NotificationsModule` needs `OrdersModule` (because `imports: [OrdersModule]`)
5. NestJS needs to create `OrdersModule` first... but that's what we started with!
6. Infinite loop → NestJS detects this and throws an error

*Teacher may ask:*

* *Why is circular dependency bad?* — The DI container cannot determine the creation order. It's like saying "A must be created before B" AND "B must be created before A" — both cannot be true.
* *Does a circular dependency only happen between 2 modules?* — No. It can be A → B → C → A (three modules forming a cycle).
* *Is this a compile-time or runtime error?* — Runtime. TypeScript compiles fine. The error happens when NestJS bootstraps and tries to build the module graph.

== 📕 Part C — Fix Circular Dependency (Method 1: `forwardRef`)

=== Step 5: Fix Module Circular Dependency with `forwardRef()`

`forwardRef()` tells NestJS: "don't resolve this import right now — wait until the full module graph is built."

.File: `src/orders/orders.module.ts` (fixed with forwardRef)
[source,typescript]
----
import { forwardRef, Module } from '@nestjs/common';
import { NotificationsModule } from 'src/notifications/notifications.module';

@Module({
  imports: [
    forwardRef(() => NotificationsModule), // ✅ Delayed resolution
  ],
  controllers: [OrdersController],
  providers: [OrdersService],
})
export class OrdersModule {}
----

.File: `src/notifications/notifications.module.ts` (fixed with forwardRef)
[source,typescript]
----
import { forwardRef, Module } from '@nestjs/common';
import { OrdersModule } from 'src/orders/orders.module';

@Module({
  imports: [forwardRef(() => OrdersModule)], // ✅ Delayed resolution
  providers: [NotificationsService],
  exports: [NotificationsService],
})
export class NotificationsModule {}
----

*How `forwardRef()` works:*

* Normal import: `imports: [NotificationsModule]` → NestJS tries to resolve `NotificationsModule` *immediately*
* `forwardRef`: `imports: [forwardRef(() => NotificationsModule)]` → NestJS stores a *callback function* and calls it *later*, after the module graph is partially built
* The arrow function `() => NotificationsModule` delays the reference — JavaScript doesn't evaluate it until NestJS calls it
* This breaks the "who comes first" deadlock

=== Step 6: Fix Provider Injection with `@Inject(forwardRef())`

Fixing modules alone is not enough — we also need to fix the *service-level* circular injection.

*Why is `@Inject(forwardRef(...))` needed at the service level too?*

There are *two levels* of circular dependency:

|===
|Level |Problem |Fix

|*Module level*
|Module A imports Module B, Module B imports Module A
|`forwardRef()` in `imports: [...]` of BOTH modules

|*Provider level*
|Service A injects Service B, Service B injects Service A
|`@Inject(forwardRef(() => ServiceB))` in the constructor
|===

You must fix BOTH levels for it to work.

*Teacher may ask:*

* *What is `forwardRef()`?* — A NestJS utility function that wraps a reference in a callback to delay its resolution. NestJS evaluates the callback during a later phase of module initialization.
* *Why do we need `forwardRef` on BOTH sides?* — Because both modules/services reference each other. If only one side uses `forwardRef`, the other side still tries to resolve immediately and fails.
* *Is `forwardRef` a good solution?* — It works but is a code smell. It means your architecture has a design problem. Method 2 (Part D) is the better approach.
* *When should you use `forwardRef`?* — Only as a temporary fix or when the circular dependency is genuinely unavoidable (which is rare).

== 📘 Part D — Fix Circular Dependency (Method 2: Refactor with Abstraction)

This is the *proper architectural solution*. Instead of `NotificationsService` calling `OrdersService` directly, we introduce an *abstraction layer* using a token-based provider.

=== Step 7a: Create the Core Module with Token-Based Provider

.File: `src/core/tokens.ts`
[source,typescript]
----
export const EVENT_PUBLISHER = Symbol('EVENT_PUBLISHER');
----

*What is happening here:*

* `Symbol('EVENT_PUBLISHER')` creates a *unique token* — a special JavaScript value that is guaranteed to be unique
* This token acts as an *identifier* for the dependency injection system
* Instead of injecting a class (like `NotificationsService`), we inject a *token* that can be bound to any implementation
* `Symbol` is like a unique key that can never clash with another key, even if they have the same description string

*Why use `Symbol` instead of a string?*

|===
|Token Type |Example |Risk

|String
|`'EVENT_PUBLISHER'`
|Two developers might accidentally use the same string in different places → conflict

|Symbol
|`Symbol('EVENT_PUBLISHER')`
|Every `Symbol()` call creates a globally unique value → impossible to conflict
|===

'''

.File: `src/core/core.module.ts`
[source,typescript]
----
import { Module } from '@nestjs/common';
import { EVENT_PUBLISHER } from './tokens';

@Module({
  providers: [
    {
      provide: EVENT_PUBLISHER,
      // ↑ The injection token — when someone asks for EVENT_PUBLISHER, give them this value
      useValue: {
        publish: (event: string, payload: any) => {
          console.log(`[CORE EVENT] ${event}`, payload);
        },
      },
      // ↑ The actual implementation — a simple object with a publish() method
      //   useValue means "use this exact object as the provider"
    },
  ],
  exports: [EVENT_PUBLISHER],
  // ↑ Export the token so other modules can import CoreModule and inject EVENT_PUBLISHER
})
export class CoreModule {}
----

*What is the `{ provide, useValue }` pattern?*

This is a *custom provider* in NestJS. Instead of the standard shorthand `providers: [SomeService]`, we define exactly what to provide and how:

|===
|Provider Pattern |Use Case |Example

|`providers: [MyService]`
|Standard — NestJS creates the class instance
|`providers: [NotificationsService]`

|`{ provide: TOKEN, useValue: obj }`
|Provide a specific value/object
|`{ provide: EVENT_PUBLISHER, useValue: { publish: ... } }`

|`{ provide: TOKEN, useClass: MyClass }`
|Provide a class (NestJS creates it)
|`{ provide: 'LOGGER', useClass: WinstonLogger }`

|`{ provide: TOKEN, useFactory: fn }`
|Provide the return value of a factory function
|`{ provide: 'CONFIG', useFactory: () => loadConfig() }`
|===

*Teacher may ask:*

* *What is a token-based provider?* — Instead of using a class as the injection key, you use a `Symbol` or string. This decouples the consumer from the implementation.
* *What does `useValue` do?* — Provides a specific object as-is. NestJS doesn't create anything — it just passes this exact object when someone injects `EVENT_PUBLISHER`.
* *Why not use `useClass`?* — `useValue` is simpler for this case since we just need a function. `useClass` would require a separate class file.
* *Could we swap implementations?* — Yes! That's the whole point. We could change `useValue` to point to a Redis publisher, Kafka producer, or email service — without changing NotificationsService.

=== Step 7b: Update NotificationsService to Use the Token

.File: `src/notifications/notifications.service.ts` (final version — no circular dependency)
[source,typescript]
----
import { Inject, Injectable } from '@nestjs/common';
import { EVENT_PUBLISHER } from 'src/core/tokens';

type EventPublisher = { publish: (event: string, payload: any) => void };
// ↑ TypeScript type definition — describes the SHAPE of the publisher object
//   Any object with a publish(event, payload) method satisfies this type
//   This is like an interface but simpler (type alias)

@Injectable()
export class NotificationsService {
  constructor(
    @Inject(EVENT_PUBLISHER)
    private readonly publisher: EventPublisher,
    // ↑ @Inject(EVENT_PUBLISHER) tells NestJS: "find the provider registered with the
    //   EVENT_PUBLISHER token and inject it here"
    //   NestJS looks up CoreModule's providers and finds the { provide: EVENT_PUBLISHER, useValue: {...} }
    //   Then injects that object here
  ) {}

  notify(event: string, payload: any) {
    this.publisher.publish(event, payload);
    // ↑ Calls the publish() method of the injected publisher
    //   Since CoreModule provides { publish: (event, payload) => console.log(...) },
    //   this will log: [CORE EVENT] receipt_created { receiptId: '...', price: 12.99 }
    return { ok: true };
  }
}
----

== ❓ Potential Teacher Questions & Answers

=== About DI

[qanda]
What is Dependency Injection?::
A design pattern where dependencies are provided (injected) by an external container instead of being created by the class itself. In NestJS, the IoC container reads constructor parameter types and automatically provides instances.

What is the IoC Container?::
Inversion of Control container — it's the "brain" of NestJS that manages creating, storing, and injecting all providers. When the app starts, the container scans all modules, reads all providers and their constructor dependencies, and builds a dependency graph.

What are the three steps to make DI work?::
1. Mark the class with `@Injectable()` — registers it with the container +
2. Add it to `providers: [...]` in its module — tells the module "I own this provider" +
3. Add the type in the constructor — NestJS reads the type and injects the matching provider

What is the difference between `providers` and `exports` in `@Module()`?::
`providers` registers the class within THIS module's scope. `exports` makes it visible to OTHER modules that import this module. A provider that is not exported is private.

=== About Circular Dependency

What is a circular dependency?::
When two or more modules/services depend on each other, forming a cycle. NestJS cannot determine which one to create first, so it throws an error.

How does `forwardRef()` fix circular dependency?::
It wraps the reference in a callback function `() => ClassName`. NestJS stores this callback and evaluates it later, after the module graph is partially constructed. This breaks the immediate resolution deadlock.

Why is `forwardRef()` not the best solution?::
It hides the architectural problem without solving it. The circular dependency still exists logically. As the project grows, more `forwardRef` calls make the code harder to understand and maintain.

=== About Part D (Refactoring)

What is a token-based provider?::
A provider identified by a `Symbol` or string instead of a class reference. You use `@Inject(TOKEN)` instead of just declaring the type. This allows injecting abstract contracts instead of concrete implementations.

What is the benefit of the CoreModule approach?::
It creates a one-way dependency flow. `NotificationsService` doesn't know about `OrdersService` at all — it only knows about an `EventPublisher` interface. This follows the *Dependency Inversion Principle* (the "D" in SOLID): depend on abstractions, not concrete implementations.

Can we swap the EVENT_PUBLISHER implementation?::
Yes! We just change `useValue` in `CoreModule`. For example, we could swap `console.log` with a Redis publisher, a Kafka producer, or a WebSocket broadcaster — without changing `NotificationsService` or any other service that uses it.

What is `Symbol()` in JavaScript?::
A primitive type that creates a globally unique value. `Symbol('A') !== Symbol('A')` — even with the same description string, every `Symbol()` call creates a new unique value. It's perfect for injection tokens because it prevents accidental collisions.
